SftpSync First-Boot Encryption Key Spec

Implementation specification for generating, storing, validating, and hiding the key used to encrypt SFTP passwords, private keys, and private-key passphrases.

Decision: Generate a 32-byte encryption key on first boot, store it in a local key file outside the database, cache it in memory after startup validation, and never expose it to the frontend or generic system-property API.

Security boundary: SFTP secrets remain encrypted in core.sftp_connection_profiles. The database stores only non-secret metadata and first-run signoff state.

Threat Model

ProtectsDatabase Exposure

  • Direct table browsing does not reveal plaintext SFTP credentials.
  • Database backups do not contain the key needed to decrypt stored credentials.
  • Accidental API, frontend, log, or debug exposure of stored rows does not reveal plaintext secrets.

Does Not ProtectHost Compromise

  • An attacker with full access to the running server can access app memory or the key file.
  • An attacker with both the database and key file can decrypt stored secrets.
  • Malicious code running inside the application process can use the loaded key.

Startup Order

  1. Run database migrations.
  2. Initialize or validate the encryption key file.
  3. Cache the validated 32-byte key in a singleton key provider.
  4. Upsert non-secret encryption metadata in core.system_properties.
  5. Set system.firstRunCompletedAtUtc if missing.
  6. Start the web app only after key initialization succeeds.

No request, background job, or SignalR workflow should be able to encrypt or decrypt SFTP secrets before this sequence completes.

Key Storage

  • Use config key Security:EncryptionKeyPath for the key file path.
  • If no path is configured, default to %LOCALAPPDATA%\SftpSync\encryption.key on Windows.
  • On macOS/Linux, default to $HOME/.sftpsync/encryption.key when HOME exists.
  • Final fallback is AppContext.BaseDirectory/.sftpsync/encryption.key.
  • The key file format is base64 text containing exactly 32 random bytes. Surrounding whitespace is ignored.
  • Never store the key material in the database.
  • Never overwrite an existing key file automatically.

First-Boot Rules

Condition Behavior
Key file exists and is valid Accept it, cache it, backfill metadata if needed, and sign off first run if missing.
Key file missing, first-run signoff missing, and no encrypted SFTP secrets exist Generate a new 32-byte key, write it with exclusive create, validate the resulting file, cache it, write metadata, and sign off first run.
Key file missing and system.firstRunCompletedAtUtc exists Fail startup. The system has already initialized and must not regenerate the key.
Key file missing and encrypted SFTP secrets exist Fail startup. Existing encrypted credentials may be unrecoverable without the original key file.
Key file exists but is malformed or not exactly 32 decoded bytes Fail startup. Do not overwrite or regenerate.

Failure Messages

  • Missing key after prior initialization: Encryption key file is missing and this system has already completed first-run initialization. Restore the key file or intentionally reset the deployment.
  • Missing key with existing encrypted profiles: Encryption key file is missing and encrypted SFTP profiles already exist. Restore the key file or delete/recreate the profiles.
  • Invalid key file: Encryption key file is invalid. It must contain base64 text for exactly 32 bytes.
  • Initializer must never include the key contents or secret contents in exception messages.

Permissions

  • Create the parent directory when it does not exist.
  • On Unix-like systems, set the parent directory owner-only where practical.
  • On Unix-like systems, create the key file with mode 0600.
  • On Windows, rely on default ACLs for this first implementation.
  • If directory or file creation fails due to permissions, fail startup with an actionable message.

Concurrency

  • Use exclusive file creation when generating the key file.
  • If another app instance creates the file first, read and validate that file instead of generating another key.
  • Metadata and first-run signoff writes must be idempotent.
  • system.firstRunCompletedAtUtc must be set only if it is missing and must never be updated on later starts.

Database Metadata

The database stores only non-secret metadata in core.system_properties.

  • security.encryptionKeyInitialized = true
  • security.encryptionKeyVersion = v1
  • security.encryptionKeyCreatedAtUtc = ISO-8601 UTC timestamp
  • system.firstRunCompletedAtUtc = ISO-8601 UTC timestamp

If a valid key file already exists and metadata is missing, startup backfills metadata. For created-at, use key file creation time when available; otherwise use current UTC time.

Encryption Behavior

  • Keep encryption and decryption in application code, not database functions.
  • Use AES-GCM as the current SecretProtector does.
  • Keep encrypted payload format v1:nonce:tag:ciphertext.
  • Do not implement key rotation in this change.
  • Remove production use of SFTPSYNC_SECRET_KEY. This is a breaking change.
  • Existing deployments must re-enter SFTP secrets or manually preserve the intended key file.
  • Do not decrypt every stored profile during startup. Validate only key file format and length.
  • If a stored secret was encrypted with a different key, fail when that secret is actually decrypted or used.

API and Frontend

  • Do not expose the key file path, key material, metadata property names, or first-run timestamp in the frontend.
  • Update /api/status to expose only safe live key state from the key provider: encryptionKeyInitialized and encryptionKeyVersion.
  • Make overall status degraded if database or encryption-key health is not available.
  • The About/Status UI may show Encryption Key: Initialized and Encryption Version: v1.
  • Remove the generic System Property editor from the frontend Settings page.
  • Keep the System Properties controller, but enforce an empty allowlist for now.
  • Return 404 NotFound for unknown, reserved, or non-editable system property names.

Services and Repositories

  • Add a dedicated security/bootstrap service for first-boot key initialization.
  • Add a singleton key provider that caches the validated 32-byte key in memory.
  • Update SecretProtector to use the key provider and throw clearly if used before initialization.
  • Reuse existing repository interfaces where practical.
  • Add HasAnyEncryptedSecretsAsync() to ISftpConnectionProfileRepository using SELECT EXISTS.
  • Add a transactional or single-method repository operation for bootstrap metadata/signoff where useful.

Logging

  • Log that a new encryption key file was created.
  • Log that an existing encryption key file is being used.
  • Log startup failure for missing key file after first-run signoff or existing encrypted secrets.
  • Log startup failure for invalid key file format.
  • Server logs may include the configured path if useful for operations.
  • Never log key contents, plaintext SFTP passwords, private keys, passphrases, or decrypted secret values.

Test Plan

  • Valid key file is parsed, validated, and cached.
  • Missing key on true first boot creates a new key file and metadata.
  • Missing key after system.firstRunCompletedAtUtc fails startup.
  • Missing key with existing encrypted profile secrets fails startup.
  • Malformed key file fails startup and is not overwritten.
  • Pre-provisioned valid key file is accepted and first-run signoff is created.
  • Concurrent startup converges on one exclusively created key file.
  • SecretProtector round-trips using the initialized key provider.
  • Tests no longer depend on SFTPSYNC_SECRET_KEY.
  • System-property API returns 404 for security metadata and unknown names.
  • Status API returns encryption initialized/version fields without key path or metadata timestamps.
