SftpSync Folder Grouping & Opaque Queue Items

Backend-driven implementation plan for first-child opaque folder grouping, recursive nested downloads, size-based progress, and requeue support.

Goal: When a sync job targets a folder, the dashboard queue shows only the immediate first-level children (folders or loose files) under the job's sourcePath. Folders are opaque — their entire subtree is hidden from the main list but downloaded recursively. Progress, status, and aggregates are maintained for the group as a single unit.

Primary tracking: Byte sizes (folder + file) rather than raw leaf-file counts.

Locked Design Decisions (from planning discussion)

1. First-child granularity (A)
Only the immediate children under the job's configured sourcePath appear as visible rows. Deeper nesting is never shown in the normal paged queue view.
2. Persistence model — Hybrid (recommended & accepted)
Store both the visible top-level opaque groups and the individual leaf files internally. UI-facing queries (and the dashboard) only ever surface the groups with aggregated stats. This enables reliable requeue, partial progress, per-file error context, and future "expand details" capability without a painful migration.
3. Progress & counting
Primary success/progress metric is bytes transferred (sum of file sizes inside groups + loose files). Integer "file counts" on runs become secondary / logical (number of visible groups + loose files at enqueue time).
4. Requeue behavior
The system must support requeuing a failed opaque folder group (and its subtree) for another full attempt. The engine can retry the group as a unit.
5. Opaque + recursive download
Folders are opaque in the UI. When the worker processes a folder group it must recursively walk and transfer the entire subtree, preserving relative structure under the job's destinationPath.

Concrete Example

Job: sourcePath = "/remote/incoming/", destinationPath = "/data/incoming/"

Remote tree at scan time:

/remote/incoming/
├── reports/
│   ├── 2026/
│   │   └── Q1-sales.pdf
│   └── summary.xlsx
├── customers.csv
└── archive/
    └── old/
        └── backup.zip

Visible opaque rows in the run's queue (paged API + dashboard table):

  • reports/ — opaque group (represents 3 files, all bytes under it)
  • customers.csv — loose file
  • archive/ — opaque group (represents 1 file deep inside)

Nothing under reports/ or archive/ ever appears as its own row in the normal queue list unless a future "expand" feature is added.

Current State (as of 2026-05-28)

  • core.download_queue_items is strictly per-file with a unique index on (job_id, remote_path).
  • No is_directory, no group_remote_path, no grouping metadata anywhere.
  • SQL functions get_download_queue_items, count_download_queue_items, and run aggregates are flat-file only.
  • Run record has total_file_count, total_bytes, etc., all currently leaf-oriented.
  • No real SFTP client or scanning worker exists yet (only development simulation that seeds flat files).
  • Dashboard QueueTable and ItemDetails assume every row is an individual file.
  • SignalR events (QueueItemUpdated, RunUpdated) are per-item.

Perfect timing — this feature can shape the design of the upcoming real SFTP sync engine.

Recommended Persistence Model — Hybrid (Details)

  • Visible groups (the opaque first-child entries) are first-class rows in download_queue_items with is_group = true (or a companion grouping column) and aggregated byte/progress fields that the worker keeps updated.
  • Leaf files are also stored (with a group_remote_path or group_id back-reference). These are never returned by the normal paged queue API unless an admin/debug "include leaves" flag is added later.
  • The unique constraint on (job_id, remote_path) remains useful and is extended naturally.
  • Run-level aggregates are computed from the groups (logical) + can optionally expose physical leaf counts if needed for auditing.
  • Requeue logic operates primarily on the group row; the worker can re-scan or resume from the leaf rows underneath it.

Why not pure "Groups only"? Requeue (#4), partial failure visibility, and future expandability become dramatically harder without leaf-level persistence. Hybrid gives us the best of both worlds with only modest extra complexity.

  • Decide on column names: is_group (bool), group_remote_path (nullable varchar), or a separate lightweight download_groups table. Hybrid leans toward adding columns to the existing table for simplicity.

Phase 1 — Schema & Migration

  • Create a new timestamped migration under SftpSync.Infrastructure/Migrations/Schema/ (e.g. 20260529xxxx_AddQueueItemGrouping).
  • Add columns to core.download_queue_items:
    • is_group boolean NOT NULL DEFAULT false
    • group_remote_path varchar(2000) NULL
    • child_count integer NOT NULL DEFAULT 0 (number of direct or total leaves — decide during design)
  • Add indexes supporting common group queries (e.g. (sync_run_id, is_group), (job_id, group_remote_path)).
  • Backfill logic or a one-time migration step for any existing data (mostly dev simulation rows).
  • Update the down-migration cleanly.

Phase 2 — SQL Functions & Aggregates

  • Update core.get_download_queue_items and core.count_download_queue_items to:
    • Filter to only is_group = true (or the equivalent top-level rows) by default for the UI-facing path.
    • Return aggregated byte progress for groups (sum of leaves underneath) when returning a group row.
    • Support the existing sort keys (status, basename, size, progress, queuedAt, etc.) on the group level.
  • Update or add helpers for run aggregate recalculation that now operate over groups + their leaf byte totals.
  • Ensure search still works sensibly against the visible group paths.
  • Add a new internal function or flag for the worker that can fetch a group's leaves when needed for requeue/resume.

Phase 3 — Backend Models, DTOs, Services

  • Add IsGroup and GroupRemotePath (nullable) to DownloadQueueItem (Domain), DownloadQueueItemResponse (Web DTO), and the TypeScript DownloadQueueItem interface.
  • Update QueueItemQuery if we need an internal "includeLeaves" mode for the worker.
  • Update DownloadQueueItemService / repository to expose a way for the worker to load a group's subtree.
  • Adjust run recalculation logic (currently in simulation + will be in the real worker) to treat groups as the primary counting unit for total_file_count while still summing all leaf bytes for total_bytes.
  • Update any existing repository integration tests that insert queue items.

Phase 4 — SFTP Scanning & Enqueue Contracts (Core Future Work)

  • Define a clean interface (e.g. ISftpDirectoryScanner or ISyncEnqueuer) that the future real worker will call.
  • The contract must accept a job's sourcePath and return a list of top-level "first child" entries (folders marked as groups + loose files).
  • For each group entry, the implementation will later recursively list and create the leaf rows linked to the group.
  • Define how byte sizes are obtained during initial scan (SFTP STAT or LIST with size) and how they flow into both group and leaf rows.
  • Document the exact grouping algorithm in comments + the plan so the future implementer cannot misinterpret "first child".

This phase can be a pure interface + unit-testable fake implementation first; the real SSH.NET / SFTP.NET client work can come in a follow-up slice.

Phase 5 — Progress, Status, Requeue & Broadcasting

  • Worker logic (when it exists) must update the group row's bytes_downloaded, current_bytes_per_second, status, etc., as leaves complete. It can either maintain the aggregate on the group row or compute it on the fly from leaves.
  • Define requeue semantics: flipping a failed group's status (and its pending leaves) back to queued (or a new requeued state) so the next poll picks it up.
  • Update DashboardBroadcaster and SignalR events so that when a group or any of its leaves change, the visible group row is broadcast (clients already treat everything as opaque).
  • Handle the case where a group completes successfully: mark the group row complete and (optionally) mark or archive its leaves.

Phase 6 — Development Simulation Updates

  • Extend the seed endpoint in DevelopmentSimulationService to insert a realistic mix of groups + leaves (e.g. the exact /remote/incoming/ tree from the example above).
  • Update the fake progress loop so that when a group row is "active", progress is applied across its leaves and the group row's aggregates are kept in sync.
  • Ensure the simulation can demonstrate a group failing and then being requeued via a dev-only "requeue group" endpoint or button.

Phase 7 — Dashboard UI (Keep It Opaque)

  • Minimal changes to DashboardPage.tsx and supporting components:
    • Update the table row to show a folder icon + trailing slash for groups (use lucide-react Folder or similar).
    • Update basename usage and the details panel to clearly label "Folder group" vs "File" and hide or de-emphasize leaf-only fields when the item is a group.
    • Progress, speed, and ETA for a group row must reflect the aggregated subtree (already coming from the backend).
    • Search, filters, sort, and pagination continue to work against the (now grouped) result set with no behavior change for the user.
  • Do not add expand/collapse in this plan unless the user explicitly asks later — keep folders opaque.
  • Update any TypeScript types and the API client if new fields appear.
  • Consider a small visual treatment (subtle background or icon) so users instantly recognize a row represents a whole subtree.

Phase 8 — Testing & Validation

  • Repository-level tests for the new grouping columns and the updated SQL functions (especially aggregation and "only groups" filtering).
  • Service and controller tests that the paged queue API never leaks leaf rows for normal callers.
  • Unit tests (or approval tests) for the grouping algorithm once the scanner contract is implemented (even if faked).
  • Update existing integration tests that seed flat queue items.
  • End-to-end simulation flow that exercises a full group lifecycle including failure + requeue.
  • Frontend tests for the (small) presentation changes in the queue table and details panel.

Phase 9 — Documentation & Polish

  • Update README.md with a short note about folder grouping behavior and the fact that large folder syncs now appear as a small number of logical rows.
  • Add a short "Grouping Rules" section or link to this plan from the docs folder.
  • Update the development simulation description if the seed data now shows groups.
  • Ensure the plan document itself is referenced from any relevant future worker implementation tickets or comments.

Milestones (Suggested Slicing)

M1. Schema + SQL + Backend Models

New migration, columns, updated SQL functions, Domain/DTO changes, repository tests green. No UI or worker changes yet.

M2. Simulation Can Seed & Drive Groups

Dev simulation inserts groups + leaves, fake progress updates group aggregates, dashboard shows the opaque groups correctly (with folder icons). Requeue dev endpoint works.

M3. Real Scanner Contract + First Worker Slice

Interface defined, fake implementation that produces correct first-child groups, real worker (or a spike) can enqueue a job's first level and recursively create leaves for groups. End-to-end with a test SFTP target or the simulation.

M4. Production-Ready Requeue, Progress, Broadcasting

Full requeue flow for failed groups, correct byte-driven run stats, SignalR updates keep the opaque group rows live, all tests passing, docs updated.

Deferred / Out of Scope for This Plan

  • UI expand/collapse to reveal leaves inside a group (future nice-to-have).
  • Per-leaf error visibility or retry in the dashboard (group-level retry is sufficient for now).
  • Path browsing or tree picker when creating/editing jobs.
  • Advanced resume strategies beyond "requeue the group".
  • Special handling for symlinks, very deep trees, or enormous single files that happen to sit in a folder.
  • Authentication/authorization around who can requeue.
