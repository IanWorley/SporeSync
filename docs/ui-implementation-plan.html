SftpSync UI Implementation Plan

Planning checkpoint for the React/TanStack UI and supporting ASP.NET Core backend APIs.

Decision: Build an integrated React UI in SftpSync.Web/ClientApp, developed with Vite and served by ASP.NET Core after publish.

Primary goal: Make the operational dashboard the home screen, centered on live sync runs and file queue progress, with secondary admin pages for jobs, connection profiles, settings, logs, and about.

Core Architecture

  • Use Vite React with TypeScript inside SftpSync.Web/ClientApp.
  • Run ASP.NET Core and Vite as separate dev processes. Vite proxies /api and /hubs to ASP.NET Core.
  • Make dotnet publish build the React app through an MSBuild target and include the built static assets.
  • Use TanStack Query, Router, Table, and Virtual.
  • Generate TypeScript types from OpenAPI, but hand-write a small fetchJson API layer.
  • Use Tailwind CSS, shadcn-style Radix components, and lucide-react icons.

Backend Foundation

  • Add read APIs for sync runs and queue items backed by core.sftp_sync_runs and core.download_queue_items.
  • Add page-number pagination, multi-status filtering, text search over remote and destination paths, and sorting by status, basename/path, size, progress, queued time, and completed time.
  • Include job name in run responses. Keep queue item responses focused on IDs, paths, progress, status, timing, retry, and error fields.
  • Add /api/status with API health, environment, current time, and database connectivity only. Do not expose connection details.
  • Auto-apply database migrations on startup in Development and Production. Fail startup hard if migrations fail.
  • Add a new migration for UI-support indexes rather than editing existing migrations.
  • Add focused indexes for run status/time, run job/time, queue run/status, and practical queue sort paths.

SignalR

  • Add one shared DashboardHub.
  • Use REST/TanStack Query as the source of truth. Use SignalR for cache updates and invalidation.
  • Support scoped subscription methods: SubscribeDashboard, SubscribeRun(runId), and UnsubscribeRun(runId).
  • Use server-to-client events named RunUpdated, QueueItemUpdated, QueueItemRemoved, and LogAppended.
  • Send complete DTOs for run and queue item update events in the first pass.
  • Throttle progress broadcasts to roughly 2-4 updates per second per active file/run, with immediate status transition events.
  • Show a subtle connection state indicator in the UI: connected, reconnecting, disconnected.

Development Simulation

  • Add development-only backend endpoints to seed deterministic sample data and start/stop a fake progress loop.
  • Persist throttled simulated progress to the database and broadcast the same DTOs through SignalR.
  • Show a clearly labeled Development-only panel in the UI using environment data from /api/status.

Frontend UX

  • Use a light, dense operations UI with dark mode available from day one.
  • Default theme follows OS preference, with a visible manual toggle persisted locally.
  • Use a collapsible desktop sidebar, icon-only collapsed mode, and mobile drawer navigation.
  • Dashboard is the operational home and includes active runs plus the selected run's queue table.
  • History reuses the same run detail and queue table components with history-oriented filters.
  • Queue rows follow the referenced file-centric model: filename, status, speed, ETA, size/progress, filters, sorting, and compact/detailed modes.
  • Use a right-side selected item details panel rather than expandable table rows.
  • Show restrained toasts for run completed, run failed, and file failed in the selected active run.
  • Show relative time in dense views and exact local timestamps in tooltips/details. History pages prioritize exact local timestamps.

Routes

  • / redirects to /dashboard.
  • /dashboard
  • /dashboard/runs/$runId
  • /runs
  • /runs/$runId
  • /jobs
  • /profiles
  • /settings
  • /logs
  • /about

Admin Pages

  • Jobs and connection profiles get create/edit forms in the first pass.
  • Connection profile secrets are write-only. The UI shows configured indicators and optional replacement fields.
  • Job paths are typed manually for now. Remote/local path browsing is deferred.
  • No delete endpoints in the first pass. Jobs can be enabled/disabled; deletion/archive policy is deferred.
  • Logs is a placeholder route initially, with SignalR contract space for LogAppended.
  • Settings includes local UI preferences and backend system properties through the existing REST API.
  • About shows app/build info where available, broad environment/status, database health, and development API docs links.

State And Behavior

  • Persist theme, sidebar collapsed state, compact/detailed mode, filters, sort, and page size locally.
  • Do not strongly persist selected run. Auto-select the newest active run, then newest recent run.
  • Wait for server responses on create/edit forms, then update or invalidate TanStack Query caches.
  • On SignalR reconnect, refetch active runs and the selected run's queue page.
  • Add basic keyboard behavior: / focuses search and Escape clears active overlays/search focus.
  • Use inline errors for forms, panel errors for dashboard load/connection failures, and toasts for unexpected background failures.

Testing And CI

  • Add frontend scripts for npm run dev, npm run build, npm run lint, and npm run test.
  • Add basic frontend checks: TypeScript build, lint, and small tests for formatting helpers and query/event cache update logic.
  • Add backend repository/service tests for run and queue queries, plus light controller tests for pagination/filter behavior.
  • Test the SignalR broadcaster/service boundary rather than full hub transport initially.
  • Update the existing GitHub Actions workflow to install Node, restore frontend packages, run frontend checks, and build the UI.

Milestones

1.Backend Foundation

Migrations auto-run, status API, run/queue repositories, services, controllers, dashboard hub, broadcaster, and dev simulation.

2.Frontend Foundation

Vite React app, routing, theme system, app shell, navigation, generated types, API client, CI, and publish integration.

3.Dashboard

Run list, queue table, filters, sorting, pagination, SignalR cache updates, details panel, notifications, and dev controls.

4.Admin Pages

Jobs, profiles, settings, logs placeholder, about page, empty states, form validation, and polish.

Deferred

  • Real start/cancel/retry queue controls.
  • Delete/archive policy for jobs and profiles.
  • SFTP/local path browsing APIs.
  • Authentication and authorization.
  • Detailed persisted logs system.
  • Cursor pagination and advanced text indexing unless performance requires them.
  • End-to-end browser tests after the UI stabilizes.
